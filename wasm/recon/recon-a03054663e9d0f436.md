# GameServer package map — /Users/fawadhaider/code/wasm64-lean4game/server

**Headline architecture finding:** this clone is the *post-v4.7.0* lean4game architecture. There is **no custom Watchdog and no custom FileWorker anymore** — the package builds **only a library** (`lean_lib GameServer`, no `lean_exe` anywhere; verified by grep). Per player, the node relay spawns **stock `lake serve --`** in the game directory (stock Lean watchdog + stock FileWorker), and all game logic runs *inside the stock FileWorker* via (a) two `@[server_rpc_method]`s baked into the game's imports and (b) a `Runner` command elab that the relay splices into every `didOpen`. The `gameserver --server` binary path in the relay is only backwards-compat for old games that ship their own copy of an older GameServer (relay checks `.lake/packages/GameServer/server/.lake/build/bin/gameserver`, `serverProcess.ts:73-99`). This is dramatically better news for a wasm64 port than the old architecture: no watchdog fork, no process spawning to replicate — the whole game contract lives in one FileWorker process + a message-rewriting proxy.

## 2. Per-level document flow

Client (`client/src/components/level.tsx:246`) opens a monaco model with URI `file:///${worldId}/${levelId}.lean` containing **only the player's tactic text**. lean4monaco connects a websocket to `/websocket/g/{owner}/{repo}` (`client/src/store/editor-atoms.ts:14-15`).

Relay rewrite, both directions in `relay/src/serverProcess.ts::messageTranslation` (lines 140-299):
- On `initialize`: stores `initializationOptions.difficulty/inventory`; **abuses `rootUri` to carry the game name** (`gameData.name` from `.lake/gamedata/game.json`) to the server (line 202-207). If client doesn't send them: defaults `difficulty=1, inventory=[]` (line 230-234).
- On `textDocument/didOpen`: parses world/level from the URI; replaces every `uri` in the message with `file://${gameDir}/Game/Metadata.lean` (a real file in the game package so the stock worker gets correct search paths); reads `.lake/gamedata/level__{worldId}__{levelId}.json` and rewrites the document text to (line 236-242):
  ```
  import {levelData.module} import GameServer.Runner 
  Runner "{gameName}" "{worldId}" {levelId} (difficulty := N) (inventory := [...]) := by
  {player content}
  ```
  Line 0 = imports, line 1 = Runner header, player content starts at line 2 → all positions shifted by `PROOF_START_LINE = 2` client→server and −2 server→client (`shiftLines`, lines 147-163, 247, 268). Server→client messages get URIs rewritten back to `file:///{worldId}/{levelId}.lean` (line 269), `semanticTokensProvider.range` capability disabled, and full semantic-token arrays re-based past line 2 (lines 272-295).
- Process model: **one stock `lake serve` process per websocket/player** (with a pre-warmed queue per popular game, `queueLength`, lines 31-36); the watchdog inside it spawns one FileWorker for the single URI `Game/Metadata.lean`. Switching levels = didClose/didOpen on the same URI → same/new worker with new content. Production wraps in `scripts/bubblewrap.sh` sandbox.

`Runner` elab (`GameServer/Runner.lean:99-162`): looks up the level via `getLevel? {game, world, level}` (from the `gameExt` persistent env extension, imported via the level module's olean); restores the level's elaboration `scope` (varDecls, attrs, open namespaces via `activateScoped`, lines 112-121); runs `findForbiddenTactics` on the player syntax; appends an invisible `skip` (empty proof) and a final `done`; then elaborates `theorem the_theorem {goal} := by {let_intros; {preamble}; {tacticSeq}}` (or `def` for non-Prop, lines 158-162). So the level's *environment* is whatever `import {level module}` provides — the level's own olean, which transitively imports `GameServer` and the game's mathlib deps. All level metadata (goal syntax, scope, hints incl. `Expr`s via `AbstractMVarsResult`) is persisted in oleans through `gameExt` (`EnvExtensions.lean:465-483`, `PersistentEnvExtension`, `asyncMode := .sync`) — no filesystem needed for that part.

**But note:** `findForbiddenTactics` (`Runner.lean:17-19`) calls `loadLevelData "." levelId.world levelId.level` — reads `.lake/gamedata/level__W__L.json` from the worker's cwd **at every recursive invocation, i.e. per syntax node** (partial def recurses with itself). This is runtime file IO inside the worker at proof-check time and needs the gamedata JSON present in the wasm worker FS (or the call memoized/replaced).

## 3. Custom RPC contract (client ↔ FileWorker)

Registered in `GameServer/RpcHandlers.lean:359-365`:
- **`Game.getInteractiveGoals`** `(Lsp.PlainGoalParams) → Option Widget.InteractiveGoals` — literally delegates to stock `Lean.Server.FileWorker.getInteractiveGoals` (the custom `GameServer.getInteractiveGoals` at line 322 exists but the RPC uses the stock one). Called from `client/src/components/infoview/info.tsx:322`.
- **`Game.getProofState`** `(GameServer.ProofStateParams) → Option GameServer.ProofState` — the workhorse (`getProofState`, lines 200-317). Params = `Lsp.PlainGoalParams` + `worldId : String` + `levelId : Nat` (line 200-203). Called from `info.tsx:317` and `goals.tsx:372` (`loadGoals`). It waits for the full snapshot list, splits the document per line, and returns per-line steps.
- Payload shapes (`GameServer/Structures.lean`, mirrored in `client/src/components/infoview/rpc_api.ts`):
  - `ProofState { steps : Array InteractiveGoalsWithHints, diagnostics : Array InteractiveDiagnostic, completed : Bool, completedWithWarnings : Bool, lastPos : Nat }` (RpcEncodable)
  - `InteractiveGoalsWithHints { goals : Array InteractiveGoalWithHints, command : String, diags, line?, column? }`
  - `InteractiveGoalWithHints { goal : GameServer.InteractiveGoal, hints : Array GameHint }`
  - `GameHint { text, hidden, rawText, varNames : Array (Name × Name) }` (plain Json)
  - `GameServer.InteractiveGoal` = stock plus `isAssumption?` on each hypothesis bundle.
- `getProofState` also synthesizes gamified diagnostics: "level completed! 🎉" / "level completed with warnings… 🎭" / "intermediate goal solved! 🎉" (`completionDiagnostics`, lines 156-198, i18n `t!` strings) and filters the "unsolved goals" error (`filterUnsolvedGoal`, 145-153). Completion = zero error diags (warnings allowed for `completedWithWarnings`), computed at lines 223-225. Hints are matched at request time against the goal via `findHints` (lines 98-143) using `matchExpr`/`matchDecls` FVar bijections and `hint.strict`.
- Beyond these two RPCs the client uses **stock** LSP/RPC: `getInteractiveTermGoal`, `Widget_getWidgets`, `getInteractiveDiagnostics` (info.tsx:323-326), plus regular didOpen/didChange/diagnostics — all shifted by the relay.
- `rc.initParams.rootUri?` is read inside `getProofState` (line 284) as the game name — the wasm port must preserve the "game name in rootUri" hack or replace it.

## 4. Game DSL & build artifacts

DSL commands in `GameServer/Commands.lean`: `Game`, `World`, `Level`, `Title`, `Introduction`, `Info`, `Image`, `Conclusion`, `Prerequisites`, `CaptionShort`, `CaptionLong`, `Languages`, `CoverImage`, `Settings (unbundleHyps := …)`, docs `TacticDoc`/`TheoremDoc … as "x" in "cat"`/`DefinitionDoc` (+ deprecated `LemmaDoc` etc.), inventory `New/Disabled/Only × Tactic/Theorem/Definition`, `NewHiddenTactic`, `TheoremTab`, `Dependency W₁ → W₂`, `Statement` (lines 400-499), and `MakeGame` (lines 553-891). Statement-body tactics: `Hint` (Tactic/Hint.lean, stores `GoalHintEntry` with abstracted goal ctx), `Branch` (Tactic/Branch.lean, evaluates then rolls back state, keeping gameExt/i18n additions), `Template`/`Hole` (Tactic/Template.lean, stores editor template with `Hole`→`sorry`), `let_intros` (Tactic/LetIntros.lean).

`Statement` elaborates the theorem for real (as `theorem <name|Game.World.levelN> sig := by let_intros; preamble; proof`) and records into the current level: `module := env.header.mainModule`, `goal := sig` (raw syntax!), `scope`, `preamble`, `descrFormat`, `statementName`, used-inventory scan (`collectUsedInventory`, Helpers.lean:117-141).

**Where generation happens:** plain `lake build` of the game package. `MakeGame` is the last command of the game's root module (e.g. `Game.lean`), runs in `CommandElabM` during elaboration — no lake facets, no separate executable. It: builds doc items from templates (docstring fallback via `getTacticDocstring` — mathlib-`#help`-style parser-state scraping, Helpers.lean:31-55; `[[mathlib_doc]]` link expansion), computes used/new items per world, world dependency graph (auto from usage + manual `Dependency` edges; loop detection `findLoops`, transitive reduction `removeTransitive` in Helpers.lean), per-level inventory tile arrays (locked/disabled/new computed at lines 729-874), previous-named-level theorems auto-unlocked, then `saveGameData` (SaveData.lean:37-65) writes to **`<gameDir>/.lake/gamedata/`** (path relative to `IO.currentDir`):
- `game.json` (Game struct + `worldSize` per world, `getGameJson` EnvExtensions.lean:430-435)
- `level__{world}__{level}.json` (`LevelInfo`: index/title/intro/conclusion/tile arrays/descrText/descrFormat/module/statementName/displayName/template/image)
- `doc__{type}__{name}.json` (`InventoryItem`)
- `inventory.json` (`InventoryOverview {tactics, lemmas, definitions, lemmaTab}`)
- copies `images/` → `.lake/gamedata/images/`; writes i18n `.pot` template (`I18n.createTemplate`).

Consumers: relay serves `.lake/gamedata` over HTTP at `/data/g/{owner}/{repo}/*` and translations at `/i18n/g/...` (relay/src/index.ts:31-85); relay itself reads `game.json` + `level__*.json` for the didOpen rewrite; `Runner` reads `level__*.json` at check time.

## 5. Tactic/theorem gating

Not by environment restriction — the full environment is imported. Enforcement is **syntactic post-hoc scan**: `findForbiddenTactics` (Runner.lean:17-94) walks the player's `tacticSeq` syntax: atoms (alpha-initial, not in `GameServer.ALLOWED_KEYWORDS` = ["with","fun","at","only","by","generalizing","using","skip","if","then","else","clear"], EnvExtensions.lean:16-17) are checked against `levelInfo.tactics` tiles (never-in-game / disabled / locked-and-not-in-player-inventory); idents resolving to theorem constants are checked against `levelInfo.lemmas ++ levelInfo.definitions`, plus a self-use check (`Structural recursion: you can't use '{n}' to proof itself!`, line 70). Severity by difficulty: 0 = silent, 1 = warnings, 2 = errors (`addMessageByDifficulty`, lines 90-94). The player's unlocked-items `inventory` comes from the client via initializationOptions (relayed into the Runner command text). It's advisory-strength gating (easily bypassed by e.g. `exact`-term-level uses of theorems only if they resolve — idents are checked — but macros/notation could slip through).

## 6. Porting-risk assessment to the qed64 wasm64 fork (4.33.0-pre)

**Green (works in a single wasm worker):**
- No custom watchdog/file-worker to port. The GameServer *library* is pure elab/meta code + two RPC handlers; the relay's per-process model collapses naturally onto qed64's single in-tab worker, since only ONE FileWorker per player ever exists anyway (single URI `Game/Metadata.lean`).
- RpcHandlers' FileWorker internals all exist unchanged in the fork (verified: `diagnosticsMutex`, `stickyDiagsRef`, `reporter`, `cmdSnaps`, `bindTaskCostly`, `withWaitFindSnap`).
- No `IO.Process` usage anywhere in GameServer. Threading is only `ServerTask`/`RequestM` machinery already exercised by qed64's worker.
- `gameExt` persistent env extension travels via oleans — compatible with baked snapshot/library-pack pipeline, *provided the game modules are compiled by the fork's toolchain* (olean format differs 4.31 vs 4.33.0-pre, so games must be rebuilt, not reused).
- The relay's message translation (`messageTranslation`) is plain JSON rewriting — portable verbatim into the JS side of the in-tab pump (between lean4monaco client and wasm worker), including the rootUri hack, +2/−2 line shifting, and semantic-token rebasing.

**Yellow (needs work):**
- `Runner`'s `loadLevelData "."` file reads at check time (and once per syntax node — fix the perf bug while porting): need `.lake/gamedata/*.json` in worker MEMFS at cwd, or patch `findForbiddenTactics` to take levelInfo once / read from `gameExt` instead.
- `Statement`-time vs play-time split: MakeGame and all Commands run at *game build* time — in the qed64 model that's the bake pipeline (native or wasm build of the game package with the fork toolchain), not the browser. Only `Runner` + `RpcHandlers` + the structures execute in-browser. Import closure of a level module = game oleans + mathlib → sized like existing qed64 packs.
- `Helpers/PrettyPrinter.lean:17` `open private ... from Lean.PrettyPrinter.Delaborator.Builtins` — build-time only (`MakeGame`→`getStatementString`), but must compile against 4.33.0-pre; check those private names still exist.
- Dependencies `batteries@v4.31.0` and `hhu-adam/i18n@v4.31.0` need bumping to fork-compatible revs; i18n does build-time file IO (`.i18n/` template writing on MakeGame — fine, bake-time) and its `t!` macro is used in `completionDiagnostics` at *runtime* — check whether translation lookup reads files lazily in the worker (game translations are otherwise served via HTTP `/i18n/...` to the client, not the server).
- Client doesn't currently send `difficulty`/`inventory` in `initializationOptions` in this build (relay warns and defaults 1/[]) — either wire through lean4monaco's initializationOptions or inject in the pump.
- 4.31→4.33 language drift in GameServer source itself (e.g. `String.Pos.Raw`, `Substring.Raw`, `text.positions` API in RpcHandlers:229-243 — this code already uses 4.31-era names that match the fork closely, but expect small compile fixes; `HashMap.get?/getD` Std vs Lean namespaces).

**Red (cannot work as-is / must replace):**
- Nothing in the GameServer package itself is red. The red parts of stock lean4game are outside it: the relay's `cp.spawn("lake", ["serve"])` process model and bubblewrap sandboxing — both replaced by qed64's in-tab worker + wasmLspInit/lsp-send pump; and `lake build` of games in-browser (not needed — bake ahead of time).
- One subtlety: `getProofState` does `doc.cmdSnaps.waitAll` — blocks until the whole file elaborates. In the wasm worker (cooperative, single-threaded pump) this demands that RPC handling not deadlock against elaboration; qed64's HARDENING notes on request/elab interleaving apply directly. `mapTaskCostly doc.reporter` additionally waits for the diagnostics reporter task — same concern.
