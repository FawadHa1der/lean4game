### What `wasmLspInit` does on the Lean side
Fork checkout **is present locally**: `$Q/pipeline/toolchain/work/lean4`, branch `qed64-wasm64` (HEAD `4a35f47`, base `cauli/lean4@5732b84`, Lean 4.33.0-pre). `src/Lean/Shell.lean`:

- `wasmLspSession : IO.Ref (Option (WorkerContext × IO.Ref WorkerState))` (line 316) — **exactly one document session per process**.
- `wasmLspInit` (`@[export lean_wasm_lsp_init]`, line 329): parses InitializeParams + LeanDidOpenTextDocumentParams; parses the doc header on the host thread; grows all cached envs' extension arrays (`ensureExtensionsSizeForWasm`, patch 0025); picks the **smallest cached environment whose import closure covers the doc's imports** (covering-env aliasing, patch 0023, with umbrella aliases `Mathlib`/`Mathlib.Tactic`/`Batteries`/`MIL.Common` satisfied by an env containing `QED64.Essential`, lines 372–388); else imports the header on this thread — failure returns **2 with the live session untouched** (patch 0027, line 399). - `wasmLspSend` (line 421): parses one `JsonRpc.Message`, runs the mainLoop bookkeeping prologue (reap finished request tasks, expire RPC sessions), then dispatches: request → `Server.FileWorker.handleRequest`, notification → `handleNotification` (`"exit"` clears the session), response/responseError → `handleResponse`/`handleResponseError`. `FileWorker.handleRequest` (fork `src/Lean/Server/FileWorker.lean:903`) routes through the normal registered handler table + `$/lean/rpc/call` machinery — so **`@[server_rpc_method]` procedures resolve from the document's environment** and need no shim/worker changes.

## 2. Boot flow — `$Q/frontend/src/qed64-boot.ts` + `main.ts`

`installArtifacts(ui)` (qed64-boot.ts:42): fetches `/profiles/index.json` (schema `qed64.profile-index/v1`), then the runtime manifest — pinned `/runtime/runtime-manifest.<__QED64_BUILD_ID__>.json` first, falling back to mutable `/runtime/runtime-manifest.json` (lines 51–56). Installs **only the `core` profile at boot** (line 65 — Mathlib elaboration is served by the umbrella snapshot; the 1 GB `essential` pack installs on demand only when a header must import from oleans). Fetches `/snapshots/index.json`.

`newSession(artifacts, ui, onDead, opts)` (line 87): re-installs any pack whose byte segments were detached by transfer to a previous worker (lines 96–111); builds `LibraryPack[]` mounted at `/lib/packs/<id>`; `leanPath` = colon-joined mount points; boots `LeanSession` (`$Q/src/runtime/client.ts:103`, worker URL `/workers/lean.worker.js`) with memory `initialBytes = (mathlib? 2048 : 256) MiB` and `maximumCandidates = memoryCandidates().filter(<= 6 GiB)` (lines 141–144; `memoryCandidates` in client.ts:290 walks 16/12/8/6/4/3 GiB by deviceMemory). Then always loads the `init` snapshot (line 151) — covering-env aliasing serves any covered header from it. `loadSnapshotByName` (line 175) is idempotent per session via `qs.loadedSnapshots`; `snapshotCacheKey` (`$Q/src/runtime/snapshots.ts:76`) = `<name>.<digest16>.snapz`.

`main.ts`: wires `WatchdogShim` into lean4monaco via the load-bearing seam at lines 239–246: `LeanMonacoOptions.websocket = { $type: "WorkerDirect", worker: {postMessage(){}}, messagePort: shim.clientPort }` — this spreads last into monaco-editor-wrapper's connection config and routes the LSP client at the MessagePort instead of a WebSocket. Buffer persisted to localStorage (`qed64.buffer`); `pagehide` → `shim.disposeForUnload()`.

**Game-agnostic vs Mathlib-specific**: the worker, `LeanSession`, profile installer (`$Q/src/install/profiles.ts` — OPFS-transactional, segment planning, SHA-256 transport verification), snapshot loader/cache, and the whole manifest format are entirely generic. Mathlib-specific bits: the alias table `UMBRELLA_ALIAS_IMPORT`/`rewriteAliasImports` (watchdog-shim.ts:123–142) and its Lean-side twin in `wasmLspInit` (Shell.lean:379–381, `QED64.Essential` marker), the `wantsMathlib` regexes (`/^\s*import\s+(Mathlib|Batteries|MIL\b)/m` in watchdog-shim.ts:357,491,604), profile ids `core`/`essential`, snapshot names `init`/`mathlib`, and the memory pre-commit sizing. A game build would add/replace a profile (GameServer+TestGame pack), a snapshot (probe `import TestGame...`), and either extend or bypass the alias table.

## 3. `watchdog-shim.ts` — client-facing LSP surface over MessagePort

`$Q/frontend/src/watchdog-shim.ts`, class `WatchdogShim` (line 151). It owns a `MessageChannel`: `clientPort` (port2) is handed to the editor's LSP client; port1 traffic goes through `fromClient` (line 636). Exact surface:
- **`initialize`** answered locally (line 637) with hardcoded `SERVER_CAPABILITIES` (lines 28–61, transcribed from `Lean.Server.Watchdog.mkLeanServerCapabilities` 4.33.0-pre: incremental sync, completion `.`, hover/defn/refs/callHierarchy/rename/workspaceSymbol/docHighlight/docSymbol/folding/semanticTokens/codeAction/inlayHint) and `serverInfo {name:"QED64 wasm64 Lean Server"}`. `initParams` are captured and replayed into every `lsp-init`. NOTE for lean4game: the real init params (incl. any `initializationOptions`) DO reach the file worker via `lsp-init`, but the initialize **response** is synthesized — game-specific server capabilities/serverInfo would need editing here.
- Swallowed notifications: `initialized`, `$/setTrace`, `workspace/didChangeConfiguration`, `workspace/didChangeWatchedFiles` (line 64). `shutdown` answered locally (line 646).
- `textDocument/didOpen` triggers session start: `prepareHeader` (line 599 — load covering snapshot, else on-demand `ensureProfile("essential")` + warm `compile` of just the header lines) then `lsp-init`; queued messages replayed with didChange version dedup (lines 728–739).
- `textDocument/didChange`: doc mirrored via `applyContentChanges` (line 93); **header edits are intercepted** (headerOf diff, line 678) and debounced 2 s into `restartForHeaderChange` (line 322) = a fresh in-place `lsp-init` (tag 2 → calm "imports incomplete" hold; tag≠0 → header-failure diagnostic via `publishHeaderFailure`, line 575); non-header edits coalesce 150 ms (`heldChange`, lines 796–809).
- **Everything else passes through untouched**: `forward` (line 823) wraps each message in `lsp-send`. There is **no method allowlist** — `$/game/*` requests/notifications, `$/lean/rpc/connect|call|release`, anything, is JSON-stringified and pumped to `FileWorker`. Server→client: every `kind:"lsp"` worker event is posted verbatim to the client port (line 234) except shim-internal `qed64-tick*` responses — so **server-initiated `$/game/loading` notifications from a game FileWorker would flow to the client unmodified**.
- Robustness machinery you get for free: per-request loss watchdog (15 s idle-server timeout synthesizes -32603; rpc calls get `-32900 RpcNeedsReconnect` on restart so the InfoView reconnects — `failInFlight`, line 306), 2.5 s `waitForDiagnostics` tickler to flush stuck stdout frames (line 244), crash-loop breaker (3 deaths/2 min, line 452), full worker-death replay (`handleWorkerDeath`, line 443: reboot session, reload snapshots from OPFS, replay didOpen + later didChanges), `$/lean/fileProgress` observation for busy/idle UI (line 260), completion fast-fail with `-32801 ContentModified` during switches (line 778).

**Could a lean4game client attach?** Yes, mechanically: lean4game's client already goes through lean4monaco (`client/src/components/level.tsx:47` exposes a `getWebSocketOptions` hook), so the same `WorkerDirect`/`messagePort` seam applies. What would need to change:
1. **Multi-document**: hard single-doc — `wasmLspSession` is `Option (ctx × state)` (Shell.lean:316) and the shim tracks one `TrackedDoc` (`this.doc`). lean4game opens one file per level, sequentially, which fits the "new didOpen = session replacement" model (a level switch = header/text change → in-place `lsp-init`), but concurrent docs are impossible without forking Shell.lean into a session map.
2. **initialize response**: synthesize the game server's capabilities (and pass through whatever lean4game's watchdog adds) instead of the vscode-lean4 set.
3. **Watchdog-level custom methods**: anything lean4game handles in its *watchdog* (not FileWorker) — e.g. loading level data from disk in `GameServer/Runner.lean` (`loadLevelData "."` reads the game dir via FS) — must be reimplemented in the shim or served by files mounted in the worker's virtual FS (a pack/MEMFS mount of the game's `.i18n`/level JSON would let the Lean-side code path work as-is).
4. **RPC**: `@[server_rpc_method]` handlers in `GameServer/RpcHandlers.lean` (lines 359, 363) ride `$/lean/rpc/call` and resolve from the doc's environment → work as soon as GameServer modules are importable in the worker. Client-observed `$/game/loading` etc. pass through.
5. **Mathlib-alias plumbing**: either add game imports to the alias/snapshot tables or neutralize `rewriteAliasImports` for the game profile.
6. **Version gap**: lean4game's `server/lean-toolchain` pins `leanprover/lean4:v4.31.0`; the fork is 4.33.0-pre (`cauli/lean4@5732b84` + 29-patch series). GameServer + TestGame must be ported/built against the fork's 4.33-era Server API (`FileWorker.WorkerContext/WorkerState` shapes, `handleRequest` signature).

## 5. Deploy story

Cloudflare Workers static assets (app shell) + R2 bucket `qed64-artifacts` (multi-GB artifacts), single origin. `$Q/infra/worker.js`: routes `/runtime/*`, `/profiles/*`, `/snapshots/*` to R2 `get`; sets COOP `same-origin` + COEP `require-corp` + CORP on **every** response (`run_worker_first = true` in `wrangler.toml` so assets get headers too); digest-named files `immutable, max-age=31536000`, manifests/indexes `must-revalidate`. `scripts/deploy-app.sh`: `npm run build:site` (frontend/ → dist/), prune `dist/{runtime,profiles,snapshots}`, `wrangler deploy` (seconds). `scripts/upload-artifacts.sh`: rclone S3 multipart `copy` (never sync — old shells keep working) of `public/{runtime,profiles,snapshots}`, with a preflight that every manifest-referenced file exists, plus the immutable `runtime-manifest.<buildId>.json` copy that makes shell↔runtime promotes atomic (DEPLOY.md "Atomic promotes": commit manifest → upload artifacts → push shell). CI: shell redeploys on push to main; artifact uploads stay manual (bakes need the 14-core local machine).

**What a second app (the game) needs**: same-origin serving with COOP/COEP (its own Worker with the same `withHeaders`, or mount under the existing origin), R2 (or shared bucket prefix) for its pack/snapshot artifacts + the runtime chunks, root-absolute paths (`/workers/lean.worker.js`, `/runtime/*`, `/profiles/*`, `/snapshots/*` are hardcoded defaults — `LeanSession` worker URL and `fetchProfileIndex`/`fetchSnapshotIndex` accept overrides), and its own `index.json`/manifests. R2 free tier headroom exists (10 GB, currently ~2.1 GB used); a game profile pack + snapshot would add low single-digit GB. Free egress makes the ~300 MB–1 GB first-visit downloads viable.

## Key risk/decision inputs
- Single-document-per-process is the deepest structural constraint (Shell.lean `wasmLspSession`); lean4game's one-level-at-a-time flow fits it, level switching maps onto the shim's in-place `lsp-init` replacement (seconds, envs stay resident).
- The shim is transparent to arbitrary JSON-RPC in both directions; only `initialize`/`shutdown`/4 notifications are consumed. Game watchdog logic that touches the filesystem must be re-homed (worker FS mount or shim reimplementation).
- Toolchain version gap (v4.31.0 → 4.33.0-pre fork) makes the GameServer port the first concrete task; everything downstream (pack → profile → snapshot → deploy) is existing, scripted pipeline.
- MEMORY.md note applies: commit locally, never git push.
